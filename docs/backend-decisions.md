# Backend decisions

Design choices for the DIGITALYCloud backend (`apps/backend`), why they were made, and what is left for operators to
decide. The HTTP contract is [05-api-reference.md](05-api-reference.md) plus the extensions listed here
([openapi.json](openapi.json) is the full machine-readable version). Status per endpoint/screen: [backend-coverage.md](backend-coverage.md).

## 1. MongoDB instead of PostgreSQL

The project requirement is MongoDB with Mongoose; it overrides the PostgreSQL proposal in the earlier docs. The relational
proposal was translated as follows.

- **Replica set always.** Multi-document transactions need one, so local development (`compose.yaml`, `npm run dev:infra`)
  runs a single-node replica set. Startup refuses a standalone server.
- **Transactions** (`withTransaction`, snapshot read concern, majority writes) wrap every multi-document invariant: signup
  (user + personal team + owner membership + billing account), service creation (slug reservation + service + env + first
  deployment + outbox entry), invitation acceptance, member removal, plan changes with their subscription item, deletion.
  **No external call ever runs inside a transaction**: Docker, Stripe, GitHub, email and storage work is queued through the
  outbox and done by workers.
- **Identifiers** are strings with a type prefix (`usr_`, `team_`, `mem_`, `dep_`, `key_`, `inv_`, `bop_` …) generated by the
  API, never Mongo ObjectIds; responses never contain `_id` or `__v`. A service's id is its immutable public slug
  (`syncbot`), unique across the platform; deleted slugs stay reserved for 30 days (`slug_reservations`).
- **Schemas** use `strict: 'throw'`, no version key, explicit indexes (`autoIndex` off). `npm run db:migrate` creates
  collections and indexes through a ledger with a lock; `indexes verify` compares declared and actual indexes;
  `indexes sync --confirm` is the only path that drops anything.
- **Money** is integer cents everywhere it is stored or charged (`priceCents`); euros appear only in DTOs for display.
  **Timestamps** are BSON dates in the database and epoch milliseconds on the wire; calendar dates are `YYYY-MM-DD`.

## 2. Work outside requests: outbox, queues, idempotency

- **Transactional outbox.** Every side effect is written to `outbox` inside the same transaction as the state change, then
  dispatched to BullMQ (Redis). A crash between commit and enqueue is recovered by the dispatcher sweep (pending entries,
  and dispatched entries whose job was lost after 15 minutes). Jobs carry the outbox id; consumers are idempotent and mark
  completion; failures retry with backoff, then go to `dead` (counted on `/internal/metrics` and the staff overview).
- **Operation generations (fencing).** A service has one active operation (deploy/start/stop/restart/apply limits/delete)
  with a lease and a generation number. Workers re-check the generation before every step that touches Docker, so stale or
  duplicated jobs cannot launch twice or overwrite newer state. Concurrent deploy requests: one wins (partial unique index),
  the others get `409`.
- **Idempotency-Key** (optional header) on `POST /services` and `POST /services/:id/deploy`: the first response is stored for
  24 h per principal and replayed for retries; a different body with the same key is `422`.
- **Duplicate processing across replicas.** API replicas are stateless (sessions in MongoDB, rate limits and streams in
  Redis). Workers share queues through BullMQ; periodic tasks are BullMQ job schedulers (one schedule per task, however many
  workers run); collectors take a
  per-server lease (`collectorLease`) so each Docker host is watched by exactly one collector. Webhook receipts are unique per
  provider event id, so retried deliveries are processed once.

## 3. Identity and sessions

- **Sessions**: opaque 256-bit token in the HttpOnly `dgc_session` cookie, only its SHA-256 stored. "Remember me": 30 days,
  sliding. Otherwise a 12-hour absolute session cookie. A password reset revokes every session; a password change revokes all
  other sessions.
- **CSRF**: unsafe cookie-authenticated requests need an exact allowed `Origin` **and** `X-CSRF-Token` equal to an HMAC of
  the HttpOnly `dgc_csrf` cookie (`GET /v1/auth/csrf` issues both). Bearer API keys and webhooks are exempt. Multipart uploads
  are covered.
- **Passwords**: Argon2id (m=19456 KiB, t=2, p=1); unknown emails hash a dummy password so timing doesn't reveal accounts.
- **Google**: OpenID Connect with PKCE, nonce and a state bound to the browser by a cookie. Linking policy: an existing
  account is linked only when Google says the email is verified **and** the local account's email is verified; otherwise
  sign-in is refused (`google_link_unverified`) to prevent takeover. If the account has TOTP, Google sign-in still asks for
  the code (the challenge travels in the URL fragment).
- **TOTP**: RFC 6238 (SHA-1, 6 digits, 30 s, ±1 step), each step accepted once (replay protection), 10 HMAC-hashed recovery
  codes. Setup is a pending secret confirmed by a first code.
- **Recent authentication**: email change, password change, account deletion and 2FA disable need the current password (or a
  sign-in within the last 15 minutes for accounts without one).
- **Email verification** is required to accept invitations and to link Google; signing in does not require it.

## 4. Teams, roles and the active team

- Signup creates a **personal team** owned by the user. Each team has exactly one owner (partial unique index + transactional
  workflows); ownership is never assigned by invitation.
- **Roles** (`packages/shared/src/permissions.ts`, used by both the API and the dashboard):

  | Action | Owner | Admin | Developer | Viewer | API key |
  | ------ | :---: | :---: | :-------: | :----: | :-----: |
  | Read services, deployments, logs, metrics, servers | ✓ | ✓ | ✓ | ✓ | read |
  | Start/stop/restart/deploy/rollback, uploads | ✓ | ✓ | ✓ | – | full (uploads: –) |
  | Create/delete services, change plans | ✓ | ✓ | – | – | – |
  | Edit settings and environment | ✓ | ✓ | – | – | full |
  | Read environment values | ✓ | ✓ | ✓ | redacted | never |
  | Team members/invitations, API keys, GitHub connection | ✓ | ✓ | – | – | – |
  | Billing pages, invoices, payment portal | ✓ | – | – | – | – |
  | Billing operation status (checkout return) | ✓ | ✓ | – | – | – |

- **Active team.** The API resolves the team per request: `X-Team-Id` header (or `?team=` on GET/EventSource, which can't send
  headers), else the session's default team (`POST /v1/teams/active`). The dashboard keeps its team **per browser tab**
  (sessionStorage) and sends it with every request, so two tabs can work in two teams without mixing data; switching team
  remounts all team state. Losing access mid-session answers `403 TEAM_UNAVAILABLE` and the tab falls back to the default team.
- Removing a member revokes the API keys they created in that team. Invitations expire after 7 days and require the
  invitee's verified email to match.
- Platform staff (`role: admin` on the user) is separate from team roles and only unlocks `/admin/*`.

## 5. Services, deployments and the runtime

- **Catalog** (`packages/shared/src/catalog.ts`) is the single source for plans, prices, limits, regions and Node versions.
  Limits are always derived from the plan; client-sent `ramLimitMb`/`storageLimitMb` are ignored. Node.js **24 LTS** (default)
  and **22 LTS** can be deployed; 20 and 18 are end-of-life and only recognised on stored services.
- **Settings vs plan**: `PATCH /services/:id` changes settings; `POST /services/:id/plan` changes the plan (billed, may need
  payment). The DTO's `pendingChanges` says what the running container doesn't reflect yet (settings → next deploy, env →
  next start, resources → being applied or failed with a reason).
- **Environment**: AES-256-GCM per value, with the service, variable id and key as associated data, under a key ring
  (`ENCRYPTION_KEYS`, rotation with `cli keys rotate`). Secret values are masked in build and runtime logs. Values are never in
  SSE payloads, API-key responses, errors or logs; viewers see them blank.
- **Sources**: GitHub (App installation; public repositories by name without one), uploaded archives (zip/tar/tar.gz,
  validated for traversal, links, device files, expansion and file count, 100 MB / 500 MB for verified Pro+ replacements),
  public Docker images (no private-network registries).
- **Docker hosts** are registered with the CLI (socket locally, mutual TLS remotely). Containers run hardened: non-root user,
  all capabilities dropped, `no-new-privileges`, PID/memory/CPU limits, **enforced disk quota** (hosts that can't enforce it
  are refused unless the development override is on), per-team bridge network, ports published only on the host's private
  address, optional gVisor runtime.
- **Pipeline**: preparing → pulling → installing → starting → health check. HTTP services must answer on `PORT` before
  traffic switches (blue/green with a drain period); a failed deployment leaves the previous version running. Workers/bots
  (no port) use a stop-then-start handoff with restore on failure. The first deployment's failure is reported as such.
- **Crash policy**: unexpected exits are recorded; paid plans auto-restart with exponential backoff (5 s doubling to 5 min);
  more than 5 crashes in 10 minutes stops restarts and marks the service failed. Free plans don't auto-restart.
- **Routing**: Traefik's HTTP provider polls `/internal/proxy/traefik` (private listener, bearer token); only healthy
  containers get routes on `{serviceId}.{PUBLIC_RUNTIME_DOMAIN}`.

## 6. Real-time and observability

- `GET /v1/events?team=` (SSE, sessions only): one stream per tab for the team's services/deployments and the user's
  notifications. Events go through Redis Streams (replay) and Pub/Sub (fan-out). Ids combine the team and user stream
  positions; browsers resume with `Last-Event-ID`. If history was trimmed the stream sends `stream.resync` and the dashboard
  reloads. `stream.revoked` closes the stream when access ends (re-checked every 30 s). `service.metrics` is live-only and may
  be dropped under backpressure; everything else is ordered and replayable.
- Runtime logs: collectors attach to containers, redact secrets, assign sequence numbers and store lines with plan-based TTLs;
  `GET /services/:id/logs/stream?since=` resumes without duplicates and sends `logs.reset` when the cursor is too old.
- Metrics: CPU % of the plan's allocation, RAM MB, network KB/s, disk MB. Live samples every 2 s in Redis; per-minute samples
  in MongoDB; history buckets (24 h hourly, 7 d 6-hourly, 30 d daily) return `null` for buckets without samples — gaps are
  never filled with invented values or zeros.
- Usage alerts at 80 % RAM/storage, debounced durably for 6 hours. Crash and deployment notifications respect each user's
  preferences.
- Logs: Pino JSON with request ids and redaction of secrets/cookies/tokens. Prometheus metrics on the private listener.
- Redis outages: commands time out after 1.5 s, so requests degrade instead of hanging; general rate limits fail open, auth
  and form limits fail closed (`503`); readiness reports the outage; connections recover automatically.

## 7. Billing (Stripe)

- One Stripe customer and at most one subscription per team, one subscription item per paid service. Prices are validated
  at startup (EUR, monthly, tax-inclusive, exact catalog amount) for every paid plan (`STRIPE_PRICES`).
- Paid changes are **billing operations**: with a card on file the prorated amount is charged synchronously (upgrades
  invoice immediately, downgrades credit the next invoice); without one, the owner is sent to Stripe Checkout and the change
  is applied when the webhook (or the checkout return poll) confirms payment. Admins without a card on file get
  `402 ownerActionRequired` and the owner is notified. A failed charge never grants resources; a resource that can't be
  created after charging is credited back (compensation).
- Webhooks are verified, stored as durable receipts (unique per event id) and processed asynchronously and in any order;
  a periodic reconciliation compares Stripe subscriptions with services. Losing entitlement (canceled/unpaid subscription)
  moves services to Free limits.
- Without Stripe configured, Free plans work and paid plans answer `503 BILLING_UNAVAILABLE`; the catalog says
  `paidPlansAvailable: false` and the dashboard disables paid choices.

## 8. API keys and rate limits

- Keys look like `dgc_live_<random>`; only a SHA-256 hash and a display prefix are stored; the secret is shown once. Keys
  belong to one team and have a `read` or `full` scope; they can't manage keys, members, billing or stream SSE. Revocation is
  immediate; `lastUsed` is updated at most once a minute.
- Redis-backed limits (per IP, per email, per user or per key): auth 10/15 min, 2FA, public forms 5/h, uploads 20/h,
  invitations, verification resends, 600 requests/min per session, 120/min per API key. `429` responses carry `Retry-After`.

| Addition | Why |
| -------- | --- |

| `GET /teams`, `POST /teams/active` | Team switcher and session default team. |
| `GET /billing/operations/:id`, `POST …/checkout`, `POST …/cancel` | Checkout return pages and pending paid changes. |
| `X-Team-Id` header / `?team=` | Per-tab team scope. |
| `Idempotency-Key` header | Safe retries of creation/deploy. |
| SSE `stream.resync`, `stream.revoked`, `logs.reset` | Honest reconnect semantics. |
| `ServiceDto.pendingChanges`, `operation`, `metricsAt`, `regionId`, `url`; nullable `branch` | Accurate state in the UI. |

| `CatalogResponse.regions[].available`, `paidPlansAvailable` | Capacity and billing availability. |

Customer-facing server data never includes Docker endpoints, private addresses or credentials (`ip` is an optional public
display address).

## 10. Frontend integration choices

- The dashboard talks only to the real API. The localStorage mock, simulated metrics/logs/deployments and seed data were
  removed (there is no mock mode or `NEXT_PUBLIC_API_MODE` switch). The landing page's dashboard preview is a captioned illustration.
- `proxy.ts` (Next.js 16) redirects dashboard routes to `/login?from=` when the session cookie is absent; it is an optimistic
  check only (the API authorizes everything; `RequireAuth` handles expired sessions). It needs the API cookie to be visible
  to the frontend host (same host, `COOKIE_DOMAIN`, or `localhost`); `AUTH_PROXY_GUARD=off` disables it otherwise.
- The status page is a Server Component revalidated every 60 seconds from `GET /status`.
- Wizard drafts survive the GitHub installation redirect without secret values; paid creation drafts (including env) are
  held encrypted by the API in the billing operation while the owner is in Checkout.

## 11. Decisions left to operators

- Stripe: products/prices, tax settings (`STRIPE_AUTOMATIC_TAX`), customer portal configuration, webhook endpoint.
- Hosting: where API/workers/collectors run, MongoDB (Atlas or self-managed replica set) and Redis (persistence, HA) providers,
  backup schedule and retention, S3 provider and bucket lifecycle.
- Runtime hosts: kernel/filesystem with quota support (XFS `pquota` or overlay2 on XFS), gVisor, registry for multi-host
  deployments, base image digests (`RUNTIME_NODE_IMAGES`), host headroom.
- DNS/TLS: wildcard certificate for the runtime domain, cookie domain for the dashboard/API pair.
- Email provider (SMTP) and sender domain authentication (SPF/DKIM/DMARC).
- GeoIP for session locations (not configured: `location` is `null` rather than guessed).
- Legal texts, data retention commitments and the support inbox.
